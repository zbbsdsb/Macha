# 对招聘定位的批评与改进建议

> 针对「First World Operator」这一职位设定本身，不是针对文档排版。
> 结论先行，然后逐条说明问题、后果与建议。严重度：🔴 会在现实中出问题 / 🟡 会削弱效果 / 🟢 可选优化

---

## 一句话结论

**这个职位的设定方向是对的——但需求里藏着一个没被承认的矛盾：简历要求这个人去体验「Macha 驱动的 NPC」，
而按仓库自己的 roadmap，那个 NPC 属于 Phase 3，一行都还没写。**
我已经在文档里用「Track A 现在可做 / Track B 核心落地后展开」的方式诚实地处理了它，
但定位本身还有四个问题会在真实招募中显形，建议在发布前想清楚。

---

## 一、🔴 会出问题：把「运维」和「体验观察」放在同一个人身上

### 问题

岗位的四合一交叉里，**Server Lead（服务器主理）** 与 **First Player / NPC Experience Researcher** 是两种
互相冲突的心智模式：

| 角色 | 默认问题 | 时间形态 |
|---|---|---|
| Server Lead | 「它还能跑吗？」 | 被动的、响应式的（崩了才动） |
| First Player | 「刚才那个瞬间为什么假？」 | 主动的、需要大段连续时间的 |

同一个人在同一个世界里会被拉向后者。运维工作的特点是**不可预测地打断**：
服务器挂了、玩家连不上、区块出错——这些都会优先占用那一段本来属于「安静观察」的时间。
更麻烦的是**心态污染**：一个刚刚修完服务器的人，进入世界时的默认心态是「检查是否正常」，
而不是「感受是否真实」。前者会让人满足于「功能正常」，从而漏掉「读起来是假的」。

### 建议

1. **在职责里明确写出时间的从属关系**：运维是**为了让实验能跑**，不是岗位本身的目标。
   文档 P04 的 01 已经写了「这不是运维岗——你是在保持这个地方可居住，好让实验能跑」，
   建议在**面试阶段口头强化**：如果候选人第一句问的是「服务器配置怎么样」，这是一个负向信号。
2. **把反馈分成两条独立通道**，不要合在一起：
   - `BREAK`（坏了）→ 走工程通道，快速处理，不进入 Experience Log
   - `FAKE`（假了）→ 走研究通道，不要求立即处理，只要求记录
   混在一条通道里，`BREAK` 会淹没 `FAKE`——因为前者更紧急，后者更重要。
3. **运维投入要设上限**。建议在内部约定「每周用于运维的时间不超过 X 小时，超出即视为需要补人或降低世界复杂度」，
   否则运维会自然膨胀并吃掉全部观察时间。

## 二、🔴 会出问题：单人 = 样本量 1，而且这个人的偏好会变成设计盲区

### 问题

「第一位」在叙事上很有力，但在方法上是**样本量 1**。后果具体而严重：

- 第一体验者的**玩法习惯**会固化成「真实感」的定义。一个偏爱社交的玩家会把「NPC 不理我」当问题；
  一个偏爱探索的玩家会把「NPC 总在同一个位置」当问题。**他们的盲区会成为整个设计的盲区。**
- 没有任何校准基准。当他说「这个瞬间很假」，团队无法判断这是**普遍的人类反应**还是**他的个人敏感点**。
- 单人离职或失去兴趣，反馈回路直接归零。

文档 P05 把「对 NPC 可信度的敏感度」列为五星权重、把「愿意长期测试」列为五星，
这恰恰放大了这个问题：**权重越高，越依赖特定一个人的主观状态。**

### 建议

1. **把「玩法风格」作为观察记录的必填元数据**。不要求技术分析，但每条 Experience Log 至少标注：
   我当时的模式（社交 / 建造 / 探索 / 战斗 / 闲逛）、我在世界里待了多久、我是否在赶时间。
   这样团队事后才能判断「这个『假』是场景相关的还是跨场景的」。
2. **目标定为 2–3 人，不是 1 人**。职位写作时可以说「第一批」而不是「第一位」，
   招募文档的标题可以仍然用 First，但内部目标是至少两位风格差异明显的运营者。
3. **文档 P06 的回路图其实已经暗示了这一点**：EXPERIENCE 节点是团队补不上的。
   补不上的节点越多越好——但前提是它们彼此不同。建议在回路图下加一个极小的 mono 标注说明这一点（可选）。

## 三、🔴 会出问题：长期、无报酬承诺、且没有终止条件的角色无法持续

### 问题

文档诚实地写了「报酬 TBD、合同 TBD、地点 TBD、工时 TBD」——**这是对的，但不够**。

这个职位的实际要求是：**连续数月、反复进入同一个世界、主动制造情境、持续写记录。**
这是一件在新鲜感过去之后才会真正开始的工作，通常是第 3–6 周。
而它目前对候选人提供的确定性是：零（没有报酬承诺、没有期限、没有「做到什么程度会变成什么」）。

结果会非常可预测：**初期申请质量不错，第 4 周开始无人进入世界，反馈回路静默中断，
而团队会误判为「这个方法不成立」——实际上只是激励结构不成立。**

### 建议

1. **给第一个周期设定明确的边界**，而不是开放式的「长期」。
   例如「第一个周期：4 周，共 X 次进入世界，产出 Y 条记录」，到期后双方重新评估。
   有限期的承诺比无限期的意图更容易被接受，也更容易被完成。
2. **把「优秀表现会带来什么」写具体**。文档现在写的是「可以逐渐成为 Macha 社区/项目的核心成员」——
   这句话在读者眼里等于没有承诺。建议至少给出一个可验证的下一步，例如：
   「周期结束后，如双方都愿意继续，会明确约定报酬与合同形式」。
   **这不虚构任何东西，只是把下一步的门打开一条缝。**
3. **给非金钱回报以具体形态**。这个岗位真正稀缺的回报是：
   署名（Experience Log 作为实验记录的公开作者）、
   影响权（他提出的实验被真的执行，且他能看到哪条记录导致了哪次架构改动）、
   以及可见的履历（AI agent / 游戏 AI 领域的一手实验参与）。
   这三样东西现在**一件都没有写进文档**。建议在 P08 补一段，这比任何福利描述都有说服力。
4. 特别提醒：**「他提出的实验被真的执行，且追溯得到」是留住这个人的关键机制**。
   如果他的记录进了黑洞，第 4 周一定会发生。

## 四、🟡 会削弱效果：Experience Log 的记录模板本身已经在要求技术分析

### 问题

需求明确说「不要要求候选人写技术分析，玩家体验优先」——这个意图是对的。
但文档 P04 的链条是：

```
SITUATION → OBSERVATION → PLAYER FEELING → WHY IT FELT WRONG → POSSIBLE CAUSE → NEXT EXPERIMENT
```

**`POSSIBLE CAUSE`（可能的原因）是一个技术判断动作。**
一个「非常懂 Minecraft 但完全不懂 AI」的玩家——也就是文档明确说更想要的那种人——
在这一栏面前会停下来，因为他不知道「原因」指的是机制、触发条件还是设计意图。
这一栏会变成两种结果：要么空着，要么编一个听起来合理的猜测。两种都在污染数据。

### 建议

把 `POSSIBLE CAUSE` 换成玩家语言的、不需要系统知识的问题。例如：

| 现在 | 建议 |
|---|---|
| POSSIBLE CAUSE | **IF I HAD TO BET**（如果要我猜，我猜是因为……） |
| NEXT EXPERIMENT | KEEP 或改为 **WHAT I WOULD TRY NEXT**（我下次会怎么试） |

「如果要我猜」明确地把猜测合法化，让玩家敢写；同时它不假装是诊断结论，
团队在使用这条数据时也会带着正确的怀疑。
`NEXT EXPERIMENT` 建议保留英文，因为它是实验设计的动作，不是诊断。

另外建议明确一句：**「第一栏可以是空的」**。要求六栏全填会让人为了填满而编造。

## 五、🟡 会削弱效果：「Find the Fake」的表述有滑回 bug 报告的风险

### 问题

文档在 P04 用了很大力气区分「报 bug」和「说清为什么假」（「Bug 报告会写『NPC 做了 X』，
你的报告要写清：为什么 X 让人感觉那里根本什么都没有」）。这段是本岗位最有力的表述之一。

但风险在于：**「Find the Fake」这个名字本身就是一个求助信号。**
猎奇式的表述会吸引以「挑错」为乐的人，而挑错的人产出的仍然是 bug 报告——只是措辞更尖锐。
文档 P05 的 NOT FOR YOU IF 部分在防这个，但防的是「只想测功能有没有跑起来」，
没有防「喜欢证明自己发现了问题」。

### 建议

1. 在 P05 的 NOT FOR YOU IF 里补一条（或改一条）：
   **「你喜欢证明自己找到了错误，而不是描述自己的困惑」** ——
   这句话能筛掉相当一部分错误的申请者。
2. 在 P07 的四个必答问题里，第 03 题（「哪一个瞬间让你觉得它是假的？」）后面，
   建议加一句极小的说明：**「说不清也是一种答案。」**
   这与需求里「能发现『这个行为很奇怪，但我暂时说不清为什么』的人」完全一致，
   而且会显著改善第一条记录的质量——它把「讲不清」从失败重新定义为有效数据。

## 六、🟢 可选：文档没有说明「进入测试世界的玩家」这一伦理问题

测试世界里会有其他玩家吗？如果有，需要一句话说明：

- 这是一个实验环境，不是普通服务器
- 他们与 NPC 的交互会被记录，用于研究
- 记录的是世界与 NPC 的行为，不针对玩家个人

现在文档完全没有提。这在实际招募中会成为一个问题（尤其如果申请者想带朋友一起进）。
建议在 P08 或 P01 底部加一行 mono 小字即可。**这不需要虚构任何东西，只是把已有的实验性质写清楚。**

## 七、🟢 可选：两个版本的使用场景应当明确

我交付了英文版和中文版。建议这样用：

| 版本 | 用途 |
|---|---|
| 英文版 | GitHub 仓库 / 项目站点 / 国际社区（Discord、Reddit 的 AI NPC 与 Minecraft 技术社区）/ 学术圈 |
| 中文版 | 中文 Minecraft 社区（服务器主理圈、模组圈、B 站/贴吧的深度玩家）/ 中文 AI 社群 |

需要注意的是：**两个版本面对的人群对「AI NPC」的既有认知差异很大。**
中文 Minecraft 深度玩家大多没有「Agent Framework」概念，这反而是好事——
文档正是要这种人。建议中文版的发布配文不要提任何 Agent / LLM 术语，
直接用「让 NPC 真的像世界里的一个人」这一句切入。

## 八、这份文档做得好的地方（不要在修改中丢掉）

写在批评之后的正面清单，因为这些是为数不多「必须保留」的部分：

1. **封面底部的四格状态条**（阶段 / NPC 能力 / 报酬 / 地点工时，后两项 TBD）。
   它在一秒内完成了「这是一个诚实且尚未成熟的项目」的沟通。这是全文档最有效的一处设计。
2. **P06「目前的真实状态」表**。把 `认知核心（真正的智能体）：尚未构建 —— Phase 3` 直接印在招募文档上，
   这在招募文档里几乎从没见过，它也几乎不可能不产生效果——对的人是加分，错的人是筛掉。
3. **P02 的四条「玩家会相信的事」**。它把「NPC 为什么假」从一个模糊的美学抱怨，
   变成了四个可以被观察、被反驳的命题。这是整个职位之所以能被评价的基础。
4. **P07 的测试任务**（「让 NPC 表现出它记得你昨天做的事，而你始终不能告诉它它记得」）。
   它测的正好是项目在意的东西，且不需要任何技术能力就能开始。
5. **P05 的「宁愿要懂 Minecraft 不懂 AI 的玩家」**。明确的价值排序比任何 JD 措辞都有用。

## 九、建议在发布前补的三件事（按优先级）

| 优先级 | 事项 | 位置 |
|---|---|---|
| 1 | 给第一个周期设定有限期 + 明确「什么算优秀」 | P08「WHAT WE CANNOT TELL YOU YET」附近 |
| 2 | 把 `POSSIBLE CAUSE` 改为玩家语言的 `IF I HAD TO BET` | P04 的 Experience Log 链条 |
| 3 | 非金钱回报的具体形态（署名 / 影响权 / 履历） | P08 |

三件都是**补充既有信息**，不涉及虚构，也不需要改动版式结构。
