## 2. 招聘定位分析

### 2.1 职位定义

| 维度 | 内容 |
|---|---|
| 对外名称 | **First World Operator** |
| 副标识 | Minecraft Server Lead / First Player |
| 本质 | Server Lead + First Player + World Operator + NPC Experience Researcher 四者的交叉 |
| 明确不是 | 服务器管理员 / 运维 / GM / QA 测试 / 社区版主 |

### 2.2 与仓库事实的对齐（这是本任务最关键的一步）

我先把文案与仓库自身的口径逐条核对，而不是照抄需求描述。核对结果：

| 事实来源 | 事实 | 对文档的约束 |
|---|---|---|
| `docs/roadmap.md` | 真实认知核心是 **Phase 3**，尚未开始 | **不能宣称已有可信 NPC 可供体验** |
| `docs/architecture.md` §1.1 | `reasoning.decide()` 返回一句硬编码字符串 | 同上 |
| `docs/roadmap.md` Phase 1C | 「环境侦察」是**唯一无前置依赖**的工作项 | 这个岗位**现在就有真活可干** |
| `announcements/2026-08-16-minecraft-experiment.md` | Minecraft 是 **Concrete Layer Test Case**，不是项目身份 | Macha 必须处于视觉与叙事中心 |
| `docs/roadmap.md` 退出判据 V1–V5 | 正确性由「边界是否成立」衡量，不由 NPC 表现是否惊艳衡量 | 不写「惊艳」「拟真」类营销语 |

### 2.3 需求描述里存在的一个真实矛盾（已解决，并在批评文档中进一步讨论）

需求要求这个职位去「体验 Macha 驱动的 NPC」「发现 NPC 不自然、不可信的瞬间」——
但按仓库自己的 roadmap，那个 NPC **还不存在**（Phase 3）。

**处理方式：把职位诚实地拆成两段，并在文档里明说。**

| 阶段 | 工作内容 | 今天的可行性 |
|---|---|---|
| **Track A（现在就能开始）** | 运营 Test Environment 01；做环境侦察；成为世界里玩家侧的在场者；建立观察与记录习惯 | ✅ 无依赖 |
| **Track B（核心落地后展开）** | 体验 NPC、找「假」的瞬间、设计实验、维护 Experience Log | ⏳ 依赖 Phase 3 |

配套做法：在 P01 封面与 P06「目前的真实状态」两处，用技术文档式的表格把成熟度直接写出来——
`NPC 能力：尚未实现`、`认知核心：尚未构建 — Phase 3`、`一个可信的、可供测试的智能体：目前不存在`。

> 这样处理之后，职位反而更有吸引力：它变成「0 → 1」而非「维护一个成熟系统的边角」，
> 同时不会因为过度承诺而在候选人进场第一天就崩掉信任。

### 2.4 核心招聘理念的落点

文档反复回扣一个问题，而不是「如何让 NPC 更聪明」：

> **「从玩家的视角出发，我们到底需要一个什么样的游戏智能体？」**

并把它拆成四件玩家会相信的事（P02）：NPC 有自己的状态 / 有自己的目的 / 记得发生过什么 /
不是在回应我。文档明确指出：**这四件事没有一件属于「智能」，它们属于「在时间里持续存在」。**
这就是把「Find the Fake」从「报 bug」提升为「回答为什么它不成立」的论证支点。

`Swiss / research lab / experimental game laboratory`。

### 4.5 标注语法（技术文档语言）

- **mono 大写 + 字距**：用于章节标签、表格列头、图示节点名、页眉页脚
- **leader dots**：表格行用等距细点连接标签与值（`Architecture and boundaries ······ defined, under revision`）
- **方角标记**：3.1pt 实心方块作为标注前缀，替代圆点/箭头符号
- **索引槽**：编号（01–05）固定在左栏槽位，正文另起对齐线
- **细线**：0.5pt；仅封面短粗线用 1.0pt
- **评级方块**：5 格实心/描边方块，替代 ★ 字形（不依赖字体符号覆盖）

### 4.6 图示语言（全部为矢量绘制）

刻意**不把箭头和方块当作字符**，而是用绘图指令生成——这样输出不依赖任何字体恰好包含某个符号。

| 图 | 形式 |
|---|---|
| 反馈回路（P06） | 垂直脊线 + 4.6pt 方角节点 + mono 节点名 + 小字注解 + 细线箭头；末节点下方出线 → 右侧返回轨 → 由上向下箭头回到首节点；轨旁 90° 旋转的 `FEEDBACK` |
| 架构栈（P06） | 四个描边方框 + 框间细线箭头；首框（Macha Core）用 accent-soft 填充 + ink 边框；第 4 框右侧接**虚线**延伸线 + 右对齐 mono 标注「未来的环境 —— 各自独立成 Layer」 |
| 职责分工（P04） | 03 用 2pt accent 竖线 + 全幅横向带强调，右侧独立「要找的是这些」列表 |
| Experience Log 链条（P04） | 六个 mono 描边小胶囊：SITUATION → OBSERVATION → PLAYER FEELING → WHY IT FELT WRONG → POSSIBLE CAUSE → NEXT EXPERIMENT |
| 封面配准刻度（P01） | 上下边缘 7 条刻度，标出自身的 6 栏网格——「实验文档自我声明其网格」这一细节 |

## 5. PDF Layout Specification（实现要点）

### 5.1 排版引擎选择

**不用 Platypus，直接用 ReportLab canvas 绘制。**
理由：Swiss 版式要求固定的栏位对齐、跨栏基准线与大量精确标注，
流式自动排版（flowable）会持续与版式对抗。canvas 的代价是需要自己实现换行与测量，
但这个代价换来的是每一页都可以精确到 0.1pt。

### 5.2 中西文混排（ReportLab 没有字体回退）

按字符逐字解析，依据各字体真实的 cmap 选择字形：

1. 汉字 / 中文标点（U+2E80–9FFF、U+3000–303F、U+FF00–FFEF 等）→ **Noto Sans SC**
2. 其余字符：若 Latin 字体 cmap 含该码位 → **Inter / Inter Display / IBM Plex Mono**
3. 否则回退到 Han 字体

这解决了箭头、`·`、`—`、`§` 等符号在不同字体间覆盖不一的问题。
（实测：Inter 缺 `▸ ◂ ▪`，Plex Mono 缺全部几何图形，Noto Sans SC 缺 `↺` ——
因此图示中的箭头与方块一律改为矢量绘制。）

### 5.3 间距约定（本项目最重要的一条工程约束）

`Doc.paragraph()` 返回的是**最后一行的下一行槽位**（而非最后一行基线）。
所有顺序排布的常量都基于这个约定做加法，块与块之间不会出现「基线相撞」。

同一原则下，**职责块的高度由一个函数同时负责测量与绘制**（`duty_metrics` / `duty_block`），
两栏对齐因此不可能因为字数变化而失配。

### 5.4 填充平衡（Fill balance）

`Doc` 记录每页内容到达的最低 y（`min_y`），页面固定件在绘制后重置该值。
构建时 `--report` 打印每页的底部余量，实测结果：

| 页 | 英文版底部余量 | 中文版底部余量 | 说明 |
|---|---|---|---|
| 01 | 18 | 18 | 封面状态条定位 |
| 02 | 104 | 95 | 分摊后的段落间距 |
| 03 | 109 | 126 | 双栏底部不对齐，属设计 |
| 04 | 45 | 41 | 全文档最满的一页 |
| 05 | 95 | 109 | |
| 06 | 28 | 28 | 架构栈底部锚定 |
| 07 | 4 | 4 | 底部锚定的 mono 行，刻意 |
| 08 | 8 | 20 | 底部锚定的收尾句 |

中文版因为汉字每行容纳字数更少、行距更高，密集页（04、06）的块间距由 `gp()`
按 0.72 系数收紧，避免溢出——这是两版唯一的结构性差异，且不影响视觉节奏。

### 5.5 布局守卫

构建过程内置三项自动检查，任一触发即向 stderr 报警：

1. 图示墨迹与架构栈上沿的净距 < 10pt
2. 右栏内容低于架构栈上沿 + 12pt
3. 架构栈自身标签被方框覆盖（由几何解耦根治：方框改为从标签基线**向下**定位，不再依赖块间距常量）

| P0 | 中文版 P06 回路节点与架构栈方框互相覆盖 | 目标位置算错符号：把「回路应结束于栈上方」写成了「栈下方」 | 按栈的真实上沿（标签基线 + 8pt）反推目标 |

布局不能在未渲染的情况下交付。本任务的每一个缺陷都是靠「渲染 → 看 → 改」发现的，
其中两项（`align="right"` 的 x 语义、目标位置的符号）在代码层面完全看不出问题。

## 8. 已知取舍与边界

| 取舍 | 说明 |
|---|---|
| **未使用 Minecraft 截图** | 需求允许「少量」使用。实际未使用，理由：Macha 必须处于视觉中心，而截图会把文档拉向「Minecraft 项目」的读感；图示承担了全部说明职能。若评审希望增加游戏侧信号，建议在 P06 加一张 1/4 版宽的截图，且必须灰阶处理 |
| **无任何人物/团队照片** | 早期项目，没有成熟的团队形象可展示，且不虚构 |
| **报酬区间留空** | 需求明确要求不虚构；P01 与 P08 两处标注 TBD |
| **8 页承载 14 个章节** | 需求要求 8 页左右。P03、P04、P05、P06 均为双主题页，密度偏高是自觉的取舍 |
| **中文版为独立文件而非双语混排** | 双语混排会显著稀释 Swiss 版式的克制感；两个独立版本各自读起来都干净 |
| **字体需下载** | `prepare_fonts.py` 首次运行需要网络（Inter 官方包 + Google Fonts）。生成的静态字体已随目录提交，日常重建无需联网 |

## 9. 如何重建

```bash
# 1) 字体（已提交，通常无需运行；无网络时可用系统字体回退）
python src/prepare_fonts.py

# 2) 生成两版 PDF
python src/build_pdf.py

# 3) 打印每页底部余量（版式平衡自检）
python src/build_pdf.py --report

# 4) 叠加版心 / 栏 / 基线网格，用于核对对齐
python src/build_pdf.py --debug-frame

# 5) 逐页光栅化 + 拼版预览到 .preview/
python src/render_preview.py --dpi 110
```

依赖：`reportlab`、`fonttools`、`pillow`、`pypdfium2`（仅预览用）。
